## Decision Log

- **DEC-001 (Stage 0):** Multi-module Maven setup with `services/api` (Spring Boot 3) and `services/tracer` (plain Java 21 runnable fat jar). Shared limits placed in `config/limits.json` and mirrored/packaged for runtime consumption.
- **DEC-002 (Stage 4 - Tracer Events & Stable Frames):** Implemented event lifecycle with `call`, `line`, `return`, `exception`, and `end` events. `FrameTracker` assigns sequentially stable 1-based `frameId`s indexed across call depth. Constructors are recorded with class name signature (e.g., `Node(int)`).
- **DEC-003 (Stage 4 - JDI Performance Caching):** User classes and caller stack frames are dynamically cached in `HeapSnapshotBuilder` and `FrameTracker`. Stack variables for caller frames are preserved without repeated IPC roundtrips while mutable heap objects are continuously traversed via object roots, yielding a 100x speedup across deep recursion (2,000 steps executed in ~1.8 seconds).
- **DEC-004 (Stage 4 - Stdout / Stderr Intercept & Cap):** `WrapperLauncher` captures merged `System.out` and `System.err`, tracking `stdoutLength` and capping output at 64 KB with `\n... [output truncated]`. `System.in` is configured with an empty EOF stream.
- **DEC-005 (Stage 4 - Safety & Limits):** Uncaught exceptions emit `exception` and `end` steps with populated `RuntimeError`. Thread creation is detected and immediately halts execution with status `unsupported`. Recursion cap (200 user frames), step cap (7,000 steps), and wall-clock timeout (5s) enforce deterministic termination.
- **DEC-006 (Stage 5 - Sandbox Hardening):** Docker container isolated with `--network none`, `--memory 512m`, `--memory-swap 512m`, `--cpus 1`, `--pids-limit 64`, `--read-only`, `--tmpfs /tmp:rw,nosuid,size=64m`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--user 10001:10001`, and `--rm`. Accommodated `--read-only` via `-XX:-UsePerfData` and `-Djava.io.tmpdir=/tmp` on both tracer and target child JVMs.
- **DEC-007 (Stage 6 - Spring Boot API Architecture):** Implemented Spring Boot 3 API with synchronous `POST /api/run` and `GET /api/health`. Bounded queue (10) and fixed concurrency pool (2 workers) return HTTP 503 on saturation. Rate limiting implemented with Bucket4j (10 req/min, 200 req/day per IP) returning HTTP 429 with `Retry-After`. Client IP extraction safely resolves `CF-Connecting-IP` before `X-Forwarded-For` with address validation. Docker runner streams stdin/stdout, enforces 20-second container kill, and produces Schema Version 1 trace JSONs on container/OOM/timeout failures. Logging records metadata only with SHA-256 hashed IPs, strictly preventing user source code or trace leakage. JVM allocated `-Xmx256m`.
- **DEC-008 (Phase 2 - Linked List Visualization & Pointer Style):** User variables referencing linked list nodes (`curr`, `prev`, `head`, `tail`, `slow`, `fast`, etc.) are rendered as upward indicator arrows directly under the target node (e.g. `↑ curr`, `↑ prev`), stacking neatly when multiple variables point to the same node. Structural links (`next`, `prev`) are rendered as explicit SVG connector arrows between node cells, with the terminal node pointing an arrow to a `null` box. Pointer changes (such as `curr.next = prev` during reversal) dynamically animate the connector arrow swinging to the new address or null.
- **DEC-009 (Phase 2 - Classification of Mixed Shapes & Ambiguous Reference Shapes):** User classes with multiple self-referencing fields that do not form a standard forward/backward pair (such as `MixedNode` with `next` and `other` in `MixedShape.java`, or candidate tree shapes with `left` and `right`) are classified as generic `object`, not as a linked list. This strictly follows PRD Section 0 Rule 4 ("Correctness over looks. A wrong 'this is a linked list' label is worse than showing the generic object view") and Section 6.2 ("A mixed case... falls back to the generic view"). Such objects remain in `leftoverObjectIds` and render honestly via `ObjectView`, avoiding misleading linear chain representations.
- **DEC-010 (Phase 2 - Mid-Operation Multi-Chain Unification):** When list operations (such as reversal, splitting, or merging) disconnect a list into multiple disjoint chains of the same node class without separate wrapper objects, `DiagramArea` unifies these chains into a single cohesive `LinkedListView` with a stable layout key. Each chain is labeled with its respective head pointer tags (e.g. `Chain 1 (head, curr)`, `Chain 2 (next)`). This prevents visual fragmentation, preserves shared coordinate space for Framer Motion transitions, and guarantees that the unreversed/disconnected portion remains fully visible within the viewport rather than disappearing or being pushed out of frame.
- **DEC-011 (Phase 2 - Severed Link & False-Positive Ghost Node Correction):** In `linkedListDiff.ts`, nodes that remain on the heap in other chains are protected from being erroneously flagged as orphaned/garbage ghosts. When a `next` pointer is reassigned (e.g. `curr.next = prev;`), the previous link target in the unreversed chain is rendered as a distinct amber dashed S-curve connector labeled `disconnected`, visually illustrating the cut pointer before the subsequent step redirects variables to advance traversal.
- **DEC-012 (Phase 2 Stage 5 - Cross-Panel Selection & Recursion Path Highlighting):** For recursive list algorithms, the top frame's node-typed local/parameter is highlighted as `[Active]` (solid blue badge and glowing border/fill), while references held by suspended caller frames along the call stack are marked with `[caller]` badges and soft highlight styling. Clicking any frame card in the Call Stack panel promotes that frame's variable tags to full prominence in the list view (`opacity: 1`, glowing ring) while dimming tags from other frames to `opacity: 0.35`. Hovering a frame in the call stack highlights referenced nodes in the diagram, hovering a tag in the diagram highlights the variable row in the Variables panel, and clicking any reference chip smooth-scrolls the visualizer directly to the target node.
- **DEC-013 (Phase 2 Stage 5 - Trace Error Schema & Test Suite Rate Limit Buffer):** `runtimeError.message` in the frontend trace schema allows null values (`z.string().nullable().optional()`) to accommodate standard Java exceptions (such as `NullPointerException` where `e.getMessage()` is null). In addition, `scripts/verify-all.ps1` incorporates a 60s token replenishment buffer prior to Gate 7 (Playwright) to prevent rate-limit (HTTP 429) exhaustion from Gates 3 & 5.
- **DEC-014 (Phase 3 Stage 1 - Parent Pointer Back-Reference Classification):** A class with exactly two self-typed child fields plus a third self-typed field named `parent`, `par`, `p`, or `up` is recognized as a binary tree node. The parent field is treated as a back-reference rather than a child link, and will be rendered as a compact parent indicator / hover link rather than an edge across the canvas. Classes with three or more self-typed fields without this specific parent back-reference pattern fall back to the generic `ObjectView`.
- **DEC-015 (Phase 3 Stage 1 - Golden Test Program Naming Disambiguation):** To avoid collision with existing Phase 2 linked-list golden tests (`SingleNode.java` and `NonStandardNames.java`), the Phase 3 tree counterparts are named `SingleTreeNode.java`, `NonStandardTreeNames.java` (using `leftChild` / `rightChild`), and `NonStandardTreeLR.java` (using `l` / `r`), preserving all Phase 2 tests and fixtures intact.
- **DEC-016 (Phase 3 Stage 2 - Cycle and Shared-Subtree Handling in Binary Trees):** When recognizing binary trees, cyclic back-edges and multiple incoming parent edges (shared subtrees / DAGs) are strictly detected:
  1. Cycles: Traversal tracks active ancestor path. Back-edges to ancestors set `hasCycle = true`, reduce confidence to `'low'`, record the edge in `brokenEdges` with reason `'cycle'`, and truncate traversal to prevent infinite loops.
  2. Shared Nodes: If a node is reached that was already visited via another parent, `hasSharedNode = true` is set, confidence drops to `'low'`, the node is kept in the hierarchy under its first parent, and the secondary parent edge is recorded in `brokenEdges` with reason `'shared'` without duplicate subtree traversal.
  3. Single Counting: All nodes in cyclic or shared components appear in `allNodeIds` and `nodeCount` exactly once.
  4. Pure Cycles: If a component has no in-degree 0 root, the entry-point node (or lowest heap ID) is designated as the primary root and the back-edge is severed.
- **DEC-017 (Phase 3 Stage 3 - Binary Tree Layout & Phantom Nodes):** Layout uses d3-hierarchy with invisible phantom nodes for missing children, ensuring left children are strictly to the left of the parent and right children are strictly to the right, with parents centered over two children.
- **DEC-018 (Phase 3 Stage 4 - Root-Anchor Layout Stability & Node Displacement Minimization):** To prevent unchanged subtrees from shifting when nodes are inserted into or deleted from other branches, `computeTreeLayout` anchors to the previous step's root (or persistent common node) coordinates when `prevLayout` is provided. If the tree expands leftward toward the canvas boundary, it smoothly shifts only enough to preserve `minX >= startX`. This achieves an average displacement of only 0.45px across 145 tree modification steps in `BstInsertRecursive.java`.
- **DEC-019 (Phase 3 Stage 4 - Binary Tree Ghost Nodes & Unreachable Object Visibility):** Deleted nodes that become unreachable stay visible for one step in a dimmed "garbage" style with dashed stroke, reduced opacity (0.45), and a small `ghost` label badge at their last known coordinates, before disappearing in the next step. This behavior is configurable via `showGhosts` (default true) and tested on BST node deletion.
- **DEC-020 (Phase 3 Stage 4 - Reachable Heap Object Collection Across All Stack Frames):** In `DiagramArea.tsx`, `rootIds` for heap reachability collection are gathered from all active frames on `step.stack` (per PRD Section 5.3: "reachable from any stack frame or static field"). This prevents caller data structures (such as trees or lists in `main`) from disappearing when execution steps into child constructors or helper functions.
- **DEC-021 (Phase 3 Stage 5 - Stack-Linked Tree Recursion, Active Node Selection, and Progress States):**
  1. *Active Node:* The top frame's parameter referencing a node in the tree is preferred as the active node (solid sky blue glow & ring). When multiple candidates exist (e.g. locals), priority names (`node`, `root`, `curr`, `current`, `n`) are checked before falling back to declaration order. If the top frame holds no tree reference, no active node is selected.
  2. *Recursion Path:* Nodes referenced by suspended caller frames are softly highlighted in purple (`isSuspended`), and connecting parent-child edges between path nodes are highlighted in sky blue (`stroke-sky-400`, 2.5px width).
  3. *Traversal Progress States:* Progress is derived deterministically from the frame lifecycle: `unvisited` (neutral), `active` (currently top frame active node), `in_progress` (suspended on call stack), and `completed` (all visiting frames have returned; rendered with soft emerald green fill and border). A small interactive legend in the header explains the states.
  4. *Step Description:* Natural step descriptions for trees recognize child traversal ("curr moved to left child" / "right child"), child insertions ("Inserted 6 as right child of 5"), and recursive calls/returns ("Called inorder(Node(3))", "inorder(Node(3)) returned").
  5. *Output Order Strip:* Stdout tokens printed so far are displayed in a bottom strip. A token is uniquely linked to a tree node only when the output token uniquely matches a single node's primary value field in the tree. Hovering or clicking links between the token and the node.
  6. *BST Order Validation:* An optional toggle "Check BST order" validates that every node strictly adheres to ancestor min/max bounds; violations are flagged with an amber warning badge.
  7. *Cross-Panel Hover & Selection:* Hovering a stack frame highlights its referenced nodes in the tree (`isHoveredFromFrame`); hovering variable chips in the Variables panel or diagram highlights the corresponding counterpart; hovering Call Tree nodes highlights tree nodes and frames.
- **DEC-022 (Phase 3 Stage 6 - Verification, Playwright E2E Suite, Examples & Supported Features):**
  1. *Examples Library:* Added 11 Phase 3 examples under category `"Binary trees"`: BST Insert (7 nodes), Inorder, Preorder, Postorder traversals, BST Search, BST Deletion (leaf, one child, two children), Tree Height, Mirror Tree, Level Order traversal, AVL Left/Right Rotation, and Wrapper BST. All examples run comfortably under the 7,000-step cap and are verified in automated test suites.
  2. *Playwright E2E Test Suite:* Added `binaryTrees.spec.ts` with 10 end-to-end tests against the real running stack: BST insert progressive growth, recursive inorder traversal with progress state transitions, deletion of node with two children via successor replacement, AVL tree single rotation, wrapper class rendering (`BST.root`), lone left child positional placement (`LeftOnly`), runtime `NullPointerException` handling, `"View as..."` manual override toggling tree to doubly-linked-list and back, `ThreeChildFields` remaining in generic `ObjectView`, and cyclic tree back-edge warning badges.
  3. *Empty State & Supported Scope:* Updated `EmptyState.tsx` to document supported binary tree/BST visualizations, detection heuristics, and explicit limitations (N-ary trees, graphs, and JDK collections like `TreeMap`/`ArrayDeque` remaining generic objects until Phase 4/5).
- **DEC-023 (Phase 4 Stage 1 - Recognition Clarifications, Heap Layout, and Linked Heaps):**
  1. *Local Variable Trio Recognition:* In addition to class objects containing array fields and int fields, recognition considers a trio of local variables in the same stack frame: an array local plus int locals with high-signal names (`top`, `front`, `rear`, `size`, `count`, `head`, `tail`) (e.g. `int[] stack = new int[10]; int top = -1;`). These are assigned low/medium confidence, allowing seamless recognition of student scripts in `main`, and can always be overridden via "View as...".
  2. *Index-Based Complete-Binary-Tree Heap Layout:* The heap's tree view uses a fixed, index-based complete-binary-tree layout (children of index $i$ at $2i+1$ and $2i+2$), distinct from Phase 3's Reingold-Tilford / tidy-tree layout. Node positions are strictly determined by index.
  3. *Node-Based Heaps:* Linked/node-based heaps and leftist heaps are not treated as array-backed heaps; they continue to be visualized as standard Phase 3 binary trees.
- **DEC-024 (Phase 4 Stage 2 - Stable Classification via TraceContext & Pure Recognition Architecture):**
  1. *Flicker-Free Classification via TraceContext:* To prevent structure classification labels from flickering between steps as execution moves in and out of helper methods (e.g. `siftUp`, `push`, `dequeue`), `buildTraceContext(steps)` extracts all user-invoked method names and indicator keywords (`min`, `max`, `smallest`, `largest`) across the entire trace once. Recognition accepts an optional `TraceContext`; when present, trace-level signals ensure stable structure labels throughout stepping. When absent (e.g. single-step tests), it falls back to the current frame stack.
  2. *Precedence & Overrides:* Candidate detection runs across both class wrappers and in-frame local variable trios. High/medium confidence candidates absorb the backing array and wrapper object from generic views. Low confidence candidates remain plain arrays/objects and emit an informational `StructureHint` ("Possibly a stack/queue/heap"). User "View as..." overrides explicitly take top priority and support synthesizing candidates on bare arrays (defaulting heap size to array length).
  3. *JDK Collections Exclusion:* Standard library classes (`java.util.*`, `javax.*`) are strictly excluded from user stack/queue/heap recognition and remain `opaque` values per Phase 4 scope.
  4. *Array Resizing Tracking:* Backing array reallocations (where the internal array ID changes across steps) are detected by comparing the array ID under the same wrapper object ID or frame variable name across consecutive steps, setting `isResized = true`.
- **DEC-025 (Phase 4 Stage 3 - Stack and Queue Visualization Architecture):**
  1. *StackView (Array-backed):* Rendered as a vertical container with slot 0 at the bottom and elements stacked upward. Occupied slots (`0..topIndex`) display values with an attached `← top` pointer chip. Free capacity slots (`topIndex + 1 .. capacity - 1`) are drawn as faint dashed empty slots so students clearly perceive unused capacity. Capacity clipping is enforced for $> 30$ slots with a prominent note ("Clipped: showing first 30 of X slots"). A toggle "Show raw array" displays the raw underlying array cells alongside the stack, exposing un-erased or garbage values past `top`.
  2. *StackView (Node-backed):* Rendered as a vertical chain of nodes descending from a labeled `top` pointer chip at the top down through `next` pointers to `null`.
  3. *QueueView (Array-backed Linear & Circular):* Rendered as a horizontal row of indexed capacity slots. Linear queues dim consumed slots prior to `frontIndex` with a struck-through "consumed" style. Circular queues highlight occupied slots across both wrapped segments and draw a curved purple dashed SVG wrap connector from the final slot underneath back to slot 0 with an arrowhead and a "wraps to 0" pill badge. When `front == rear`, markers are neatly grouped in a single column without overlapping.
  4. *QueueView (Node-backed):* Rendered as a horizontal chain of nodes with an attached `front` pointer chip on the head node and `rear` pointer chip on the tail node.
  5. *StructureHeader & Overrides:* Both `StackView` and `QueueView` share `StructureHeader`, which displays class/variable names, non-structural fields (`capacity = 8`, `size = 3`), state badges (`Empty`, `Full`, `count = X`, `Wraps around`, `Resized`), a confidence badge with hover tooltip detailing detection reasons, a raw array toggle, and the `ViewAsMenu` dropdown (offering Array, Stack, Queue, Heap (disabled), Linked list, Binary tree, Generic object).
  6. *DiagramArea Integration & Error Boundary Fallbacks:* `DiagramArea` consumes `recognition.stacks` and `recognition.queues`, wrapping each in a `VisualizerErrorBoundary` with fallbacks to `ArrayView` or generic `ObjectView`. All earlier visualizers (lists, trees, grids, arrays, objects) remain completely unchanged.
- **DEC-026 (Phase 4 Stage 4 - Stack & Queue Diffing, Honest State Animations, Wraparound & Resizing):**
  1. *Pure Structure-Level Diffing (`stackQueueDiff.ts`):* Implemented `computeStackDiff` and `computeQueueDiff` as pure functions comparing `prevStructure` and `currStructure` (and their heaps). Detects operations (`push`, `pop`, `enqueue`, `dequeue`, `modify`, `resize`, `none`), mutated cells (`changedSlots`, `writtenSlot`), changed markers (`top`, `front`, `rear`, `count`, `size`), resizing transitions, circular queue wraparound events, and ghost nodes. Benchmark performance on a 30-slot stack and queue is 0.0116 ms per step (well below the 5.0 ms threshold).
  2. *Honest Diffs & Stale Slot Semantics:* For array-backed stacks and queues, pops and dequeues in Java often decrement pointers without zeroing the array cell. Rather than faking disappearance, the slot transitions to a dimmed "stale" appearance with an explicit `(stale)` or `consumed` badge and faint value display. A floating pop/dequeue chip concurrently animates out (upward for stacks, toward front for queues). When overwritten or cleared, the slot updates honestly to its new state.
  3. *Circular Queue Wraparound Highlighting:* When `rear` or `front` wraps around modulo capacity from `capacity - 1` to `0`, `isWrapTransition` highlights the SVG wrap connector with a glowing stroke and displays an animated badge (`rear wraps to 0` or `front wraps to 0`), while the wrapped marker highlights at slot 0.
  4. *Array Resizing Transitions & Badge:* When backing arrays double/reallocate (new heap id, larger length), `isResized` displays a badge `resized: capacity 2 → 4` in `StructureHeader`. Elements transition into their new slots while preserving wrapper identity.
  5. *Bidirectional Navigation & Playback Speed Scaling:* `isBackward: true` reverses operations cleanly (pushed elements leave as pops, popped elements return, resize shrinks capacity 4 → 2). Framer Motion duration is computed via `getAnimationDuration`: 0 for `prefers-reduced-motion`, 50ms at 4x playback (preventing visual accumulation/queuing), 120ms at 2x, and 280ms at 1x.
  6. *Phase 2 Ghost Rule Reuse:* Node-backed stacks and queues retain removed, unreachable nodes for 1 step as dimmed ghost nodes (`(popped)` or `(dequeued)`), providing visual continuity before fading out.
- **DEC-027 (Phase 4 Stage 6 - Heap Animation, Derived Value Tokens, and Intermediate Swap States):**
  1. *Derived Value Tokens & Minimal-Movement Matching (`heapDiff.ts`):* Value tokens are keyed by derived identity to enable authentic physical travel across stepping. To resolve ambiguous duplicate values without impossible cross-array jumps, `computeValueMatching` executes a two-tier matching algorithm:
     - Tier 1: All cells where `prev[i] == curr[i]` match with distance 0 and zero motion.
     - Tier 2: Unmatched elements of identical value are matched using 1D order-preserving minimum-cost dynamic programming ($DP(i, j) = \min(DP(i, j-1), DP(i-1, j-1) + |P[i-1] - C[j-1]|)$), guaranteeing strictly non-crossing travel paths and minimal total displacement.
  2. *Swap Animation & Equal-Value Swaps:* When two cells exchange values between consecutive steps, the value tokens fly between the two cells in `HeapArrayView` ($(dx, 0)$) and between the two tree nodes in `HeapTreeView` ($(dx, dy)$) simultaneously. When equal values are swapped (`HeapWithEqualValues`), no impossible motion is rendered; both cells/nodes pulse with an amber highlight ring and the step description reports `"Swapped equal values at index [u] and [v]"`.
  3. *Honest Intermediate States vs Helper Swaps:* JavaScope never fakes an intermediate state. In inline swaps (`HeapInlineSwap`):
     - Line 1 (`temp = a[i]`): `temp` renders as an animated floating chip above the heap row.
     - Line 2 (`a[i] = a[p]`): Cell $i$ receives the token from cell $p$, and both cells honestly display identical values while `temp` retains the old value.
     - Line 3 (`a[p] = temp`): Cell $p$ receives the value from `temp`, completing the swap.
     Helper `swap(i, p)` methods animate as a single complete 2-way swap on the step where the exchange finishes.
  4. *Insert, Extract & Sift Paths:* Tree nodes fade in on insertion and fade out on extraction as `size` changes. Sift-up and sift-down animate the exact sequence of swaps executed by the bytecode up or down the complete binary tree.
  5. *Live Violations & Sorted Region:* Heap-property violation edges update in real time as swaps resolve order defects. For heapsort (`HeapSortBareArray`), slots $j \ge \text{size}$ are marked with a green `"sorted"` badge and dimmed as the tree shrinks.
  6. *Resizing & Performance:* Capacity increases trigger `"resized: capacity N → 2N"` badges. Playback at 4x reduces animation duration to 50ms without queuing. Benchmark on a 31-element heap (`HeapFull31`) executes diff and layout in 0.0815 ms per step, well within the 16.6 ms (60 FPS) frame budget.
- **DEC-028 (Phase 4 Stage 7 - Stacks, Queues, Heaps Final Integration, Step Descriptions, Examples & Verification):**
  1. *Call-Stack & Variables Cross-Highlighting:* Hovering a stack frame in the Call Stack panel or an active variable chip in the Variables panel calculates reachable slots, array cells, and tree nodes (`hoveredFrame`, `hoveredVariableName`, `hoveredFrameNodeIds`) across `StackView`, `QueueView`, and `HeapView`, illuminating referenced elements with vivid highlight rings and chips.
  2. *Index Pointer Variable Labels:* Integer variables in the Variables panel with values within the bounds of an active structure are annotated with `→ cell {n}` (e.g. `i = 3 → cell 3`, `top = 2 → cell 2`, `front = 1 → cell 1`), bridging local variables and visual cells.
  3. *Deterministic Step Descriptions:* Natural step descriptions are generated deterministically by comparing consecutive execution steps:
     - Stack: `"Pushed 5 onto the stack"` / `"Popped element from the stack"` / `"Stack top moved to index 3"`.
     - Queue: `"Enqueued 10 into the queue"` / `"Dequeued 3 (front moved to index 2)"`.
     - Heap: `"Inserted 15 into the heap (size is now 5)"` / `"Extracted min element from heap"` / `"Swapped heap[1] and heap[4]"` / `"Heap size is now 6"`.
  4. *Phase 4 Examples Library:* Added 10 golden examples under category `"Stacks, queues, heaps"`:
     - Stack push/pop array (`stack-array`)
     - Stack push/pop node (`stack-node`)
     - Bracket matching (`bracket-matching`)
     - Postfix evaluation (`postfix-eval`)
     - Circular queue (`circular-queue`)
     - Queue from two stacks (`queue-from-two-stacks`)
     - Min-heap insert (`min-heap-insert`)
     - Min-heap extract (`min-heap-extract`)
     - Build-heap / heapify (`heapify`)
     - Heap sort bare array (`heap-sort`)
     All examples complete comfortably within the 7,000-step ceiling and are verified in automated harness tests.
  5. *Empty State & Supported Scope Updates:* Updated `EmptyState.tsx` to document supported stack, queue, and heap visualizations, confidence tiers, and "View as…" manual overrides. Explicitly documented that JDK collections (`java.util.Stack`, `java.util.ArrayDeque`, `java.util.PriorityQueue`, `java.util.ArrayList`, `java.util.HashMap`) remain opaque reference cards until Phase 5.
  6. *Visualizer Error Boundaries:* Wrapped all stack, queue, and heap visualizers with `VisualizerErrorBoundary` falling back to plain array or object cards if unexpected corrupt states occur, ensuring zero UI crashes.
